## Alcance y riesgo aceptado localmente

Los dispositivos autorizados de la misma Wi-Fi abren `http://IP_PRIVADA_DE_EMA:3001`. HTTP transmite sin cifrar contraseñas, tokens, información y fotografías; tampoco autentica el servidor ante un intermediario. Wi-Fi protegida, dirección privada y firewall acotado reducen exposición, pero no equivalen a HTTPS. El operador decide si acepta este riesgo antes de arrancar y de escribir datos reales. Si no lo acepta, debe preparar HTTPS y otro release aprobado. No usar red pública, invitados, reenvíos del router, túneles ni publicación en Internet.

El gateway Nginx es la única publicación: `LAN_IP:3001 → 80/tcp`. Sirve frontend, `/api/` y lecturas GET/HEAD del bucket con firma. API, PostgreSQL, MinIO y consola no publican puertos. Redes internas separan DB y aplicación; sólo gateway integra la red de ingreso. Los volúmenes son persistentes y exclusivos del proyecto Compose; ningún volumen externo o de QA se incorpora.

La API conserva `NODE_ENV=production`, snapshot de configuración, guard del cliente Prisma, JWT/OTP independientes, guards, membresías, capabilities, auditoría y aislamiento por Business. `TOP_DEPLOYMENT_PROFILE=lan-pilot` exige IPv4 RFC1918 canónica, puerto 3001, un único origen CORS, S3 interno `http://minio:9000`, URLs públicas por el mismo gateway y base `postgres:5432/top_pilot`. El modo estándar sigue exigiendo HTTPS/SMTP. No se admite cambiar `NODE_ENV` para eludir validaciones.

Correo queda deshabilitado. Registro, reenvío, verificación y recuperación devuelven `503 EMAIL_FEATURE_DISABLED` antes de consultas de elegibilidad, generación de tokens o escrituras. No se construye SMTP ni emisor de consola; no se muestran OTP o enlaces. Login, refresh, logout y perfil de una cuenta ACTIVE ya verificada conservan sus reglas. Una cuenta sin verificar sigue sin poder ingresar. Este candidato incorpora el cierre coordinado de cambio de correo: `409 EMAIL_CHANGE_UNAVAILABLE` para cambios efectivos, validando SELF/ACTIVE; el mismo correo normalizado admite no-op sin escrituras ni tokens. El cierre es independiente del transporte. No recuperar contraseñas por SQL ni verificar cuentas artificialmente.

## Secretos e inventario del release

Copiar `.env.pilot.example` a una carpeta protegida **fuera del repositorio y de cualquier carpeta Git**. Completarla localmente mediante un editor seguro; los scripts no generan credenciales. El ejemplo contiene valores vacíos y no permite iniciar. Restringir ACL al operador, SYSTEM y Administrators. No colocar el archivo dentro del paquete, imágenes, chats, backups públicos o argumentos de línea de comandos.

`PILOT_PROJECT` debe ser exclusivo, con formato `top-pilot-<sufijo>`; nombres `top-pilot-restore-*` quedan reservados para clones. `PILOT_SOURCE_COMMIT` identifica el artefacto final del manifiesto. Las cinco imágenes (`API_IMAGE`, `FRONTEND_IMAGE`, `POSTGRES_IMAGE`, `MINIO_IMAGE`, `HELPER_IMAGE`) deben usar digest `@sha256:` o ID local `sha256:` completo, disponibles localmente. `HELPER_IMAGE` necesita `sh`, `tar` y `sha256sum`; puede ser el mismo PostgreSQL 16 Alpine fijado. No reutilizar nombres, imágenes mutables o volúmenes de QA.

PostgreSQL separa propietario `top_pilot` y rol API `top_pilot_app` conforme al procedimiento siguiente; la base sigue siendo `top_pilot`. No pegar una URL real en un comando. JWT y OTP deben tener al menos 32 bytes cada uno y ser independientes. MinIO exige administrador separado de la credencial de aplicación, limitada exclusivamente al bucket privado; no asignar el administrador a `S3_ACCESS_KEY`. `S3_BUCKET` usa `top-pilot-<sufijo>` en minúsculas, dígitos y guiones, hasta 63 caracteres, para evitar colisiones con rutas de la UI/API. Los scripts sólo comprueban diferencias y formato: la política efectiva requiere validación del operador.

### PostgreSQL: propietario de mantenimiento y rol API

`MIGRATION_DATABASE_URL` usa `postgresql://top_pilot:<contraseña-codificada>@postgres:5432/top_pilot?schema=public` y coincide con `POSTGRES_PASSWORD`. Sólo el migrador recibe esa conexión propietaria; backups/restores usan el propietario por socket privado. `DATABASE_URL` usa `postgresql://top_pilot_app:<otra-contraseña-codificada>@postgres:5432/top_pilot?schema=public`, con contraseña propia de al menos 32 bytes, distinta del propietario y de los demás secretos. Ambos valores los elige y escribe el operador en el archivo protegido. La API no recibe la conexión ni la contraseña de mantenimiento.

Después de `Migrate.ps1`, con API/gateway detenidos, ejecutar `windows/Provision-AppRole.ps1 -EnvPath $taskPilotEnv -MaintenanceApproved -ReleaseApproved`. Requiere infraestructura propia preparada y ausencia de otras conexiones. El SQL concede SELECT/INSERT/UPDATE/DELETE sobre tablas y USAGE/SELECT sobre secuencias de `public`; concede sólo CONNECT y USAGE de schema, sin CREATE, TEMP, TRUNCATE, GRANT OPTION, propiedad, membresías, SUPERUSER, CREATEDB, CREATEROLE, REPLICATION ni BYPASSRLS. Excluye `_prisma_migrations` y retira CONNECT/TEMP en `postgres`/`template1`; el propietario bootstrap conserva mantenimiento. Rechaza otras bases no aprobadas en este cluster exclusivo. Conserva restricciones, auditorías y aislamiento de aplicación por Business. Aplica grants actuales y por defecto para objetos futuros creados por `top_pilot`. Un propietario inesperado, membresías o funciones de usuario SECURITY DEFINER exigen revisión; no se borran objetos ni se cambian sus dueños. [PostgreSQL distingue privilegios existentes y futuros](https://www.postgresql.org/docs/16/sql-alterdefaultprivileges.html).

El script termina siempre con `top_pilot_app NOLOGIN`, sin asignar contraseña. Devuelve ID del contenedor propio y contexto Docker local ya validados. El operador abre una consola local en ese contexto/contenedor exclusivamente, sin transcript/debug, mediante `docker --context CONTEXTO_LOCAL_VALIDADO exec -it ID_POSTGRES_PROPIO psql -X --no-password -U top_pilot -d top_pilot`. Dentro de psql ejecutar `SET log_statement='none'; SET log_min_error_statement='panic'; SET log_min_duration_statement=-1;`, luego `\password top_pilot_app`: el prompt oculto debe recibir la misma contraseña que ya eligió para `DATABASE_URL`, sin escribirla en SQL, argv, historial, logs o chats. Sólo tras completar ese paso, ejecutar `ALTER ROLE top_pilot_app LOGIN;` y salir con `\q`. No usar contraseñas de ejemplo ni ampliar permisos. [El comando psql evita contraseña plaintext en historial y logs](https://www.postgresql.org/docs/16/app-psql.html). Esta intervención no fue ejecutada por el agente.

`Start.ps1` bloquea la publicación si falta LOGIN, contraseña asignada o política de catálogo/ACL correcta, incluyendo acceso a otras bases. Mantiene el gateway detenido, arranca sólo API y exige autenticación SQL desde su contenedor mediante Prisma y su `DATABASE_URL` privado: una consulta fija debe devolver `top_pilot` y `top_pilot_app`. El código viaja por stdin, no imprime URL/contraseña, descarta errores sensibles y exige marcador exacto tras desconexión; limita la consulta a 10 segundos y el cliente Docker a 20. Sólo entonces inicia gateway y verifica health/listener. Una contraseña diferente, rol/base incorrectos, fallo de conexión o timeout detiene API/gateway propios y conserva datos. Health por sí solo confirma proceso vivo y no autentica PostgreSQL. Restore usa `--no-owner --no-privileges` y repone los grants mínimos únicamente en el clon técnico mediante el mismo SQL: el rol queda NOLOGIN, sin contraseña asignada y sin API; exige revisión e intervención local antes de cualquier uso. El clon permanece detenido al terminar; no se activa LOGIN ni se reabre automáticamente. No afirmar que el rol mínimo sustituye HTTPS o los guards de tenant.

MinIO inicia sin aprovisionamiento automático. Un administrador local debe crear el bucket privado y la credencial suministrada por el operador mediante una herramienta fijada y autorizada, usando entrada protegida, sin contraseñas en argv ni logs. `storage-policy.template.json` describe el permiso mínimo de Get/Put/Delete dentro del bucket; reemplazar sólo el nombre validado del bucket. No habilitar lectura anónima ni montar consola o Docker socket. Registrar prueba sintética de subida/lectura firmada y rechazo anónimo/cross-bucket. Este paquete no crea usuarios MinIO, cuenta TOP ni secretos.

`release-manifest.json` contiene commit, referencias de imágenes, hashes de archivos y estados de gates. El integrador completa las imágenes/evidencias después de construir y probar el código final; el operador registra aprobación explícita. No convertir `NOT_RUN` en `PASS` por el horario. ## Backup coherente y restauración a un clon

Antes de la primera escritura, mantenimiento y según horario acordado, cerrar nuevos ingresos y avisar a usuarios. Backup detiene gateway/API con plazo de drenaje, obtiene dump PostgreSQL custom sin stdout y detiene MinIO para archivar coherentemente su volumen, incluida metadata. El helper de backup sólo añade `DAC_READ_SEARCH` para leer archivos de otros UID: origen propio read-only, destino nuevo con ACL restringida, sin red, rootfs read-only y las demás capabilities retiradas. No añade `DAC_OVERRIDE`, `FOWNER` ni permisos de escritura al volumen de origen. Si el runtime Docker no admite esa capability, el backup queda incompleto y se bloquea el uso real hasta resolver y ensayar el procedimiento; no sustituirla improvisando privilegios. Guardar dump/objetos/inventario como conjunto con hashes, esquema/release y versiones. Mantener el destino con ACL restringida y copia protegida fuera del disco activo; los archivos **no se cifran automáticamente** y contienen credenciales/hashes/sesiones y datos sensibles. Los secretos de recuperación se custodian por separado.

```powershell
$taskPilotBackups = 'RUTA_ABSOLUTA_DESTINO_PROTEGIDO_FUERA_DEL_DISCO_ACTIVO'
& (Join-Path $taskPilotRoot 'windows/Backup.ps1') -EnvPath $taskPilotEnv -Destination $taskPilotBackups -MaintenanceApproved
# Sólo después de revisar backup y terminar mantenimiento:
& (Join-Path $taskPilotRoot 'windows/Start.ps1') -EnvPath $taskPilotEnv -ReleaseApproved -AcceptHttpRisk -AccountReady

$taskPilotSet = 'RUTA_ABSOLUTA_CONJUNTO_BACKUP'
& (Join-Path $taskPilotRoot 'windows/Restore.ps1') -EnvPath $taskPilotEnv -BackupDirectory $taskPilotSet -Project 'top-pilot-restore-sufijo-nuevo' -RestoreApproved
```

Restore rechaza un proyecto/volumen existente. Inicia PostgreSQL aislado y crea MinIO detenido para extraer sobre un volumen vacío; después de restaurar, inicia MinIO sólo para verificar health y detiene todo el clon al terminar. No inicia API/frontend/correo ni publica puertos host; restaura a una DB/bucket nuevos y conserva originales. No aplica `--clean`, migraciones, seeds o rollback SQL. La copia cruda de MinIO exige el mismo digest y configuración compatible; no promete portabilidad entre versiones. Antes de crear el clon, valida metadata tar y compatibilidad UID/GID con la imagen MinIO: admite archivos/directorios ASCII sin espacios, ustar y GNU LongName de hasta 4095 bytes incluido el terminador, sin metadata GNU extra; rechaza links, traversal, PAX, tipos especiales y modos superiores a 0777. Estos límites deben ensayarse con la metadata interna de la imagen final. El helper extrae temporalmente como UID 0 para comprobar hashes, conserva los modos y aplica/verifica cada UID/GID desde las hojas hacia la raíz. Sólo esta operación sobre el volumen nuevo detenido puede añadir `CHOWN`; mantiene red deshabilitada, rootfs read-only, backup read-only y las demás capabilities retiradas. Una imagen no root debe declarar UID:GID numéricos coincidentes y permisos de propietario de lectura/escritura, más traversal para directorios. Para una imagen root con propietarios mixtos, verificar también sus capabilities reales y acceso a todos los objetos antes de aprobar; no asumirlo por el health. No improvisar chmod/chown del volumen real para eludir un fallo; ajustar y ensayar el procedimiento antes de aprobar. Comprueba hashes, UID/GID/modos, conteos PostgreSQL y salud técnica de MinIO; la reconciliación de relaciones, reservas, pagos, saldos, auditorías y keys se realiza sobre el clon antes de cualquier recuperación real. Estos controles no prueban firma S3, cuenta o operatividad de TOP. [PostgreSQL explica el formato custom y pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html).

Si backup/restore falla, los scripts no reabren automáticamente la operación y conservan artefactos/volúmenes para investigar. No usar `down -v`, `prune`, DROP/TRUNCATE, reset ni borrar originales. Dumps periódicos no garantizan pérdida cero ante fallo de disco: acordar RPO/RTO reales y registrar duración del ensayo.
